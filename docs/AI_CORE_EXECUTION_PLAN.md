# AI CORE — план до работещ продукт

Този документ е работният план за затваряне на един цялостен контур. Всяка
следваща фаза се приема само след тестове и реална проверка; нова функция не
замества незавършена предишна.

## 1. Стабилен разговор и памет — прието

- Разговорът пази контекста в сесията и възстановява последните съобщения след
  презареждане.
- Firestore е единственият production backend за памет и operational state.
- Потвърждението за запис/изтриване на паметта остава отделна защитена граница.

## 2. Устойчив Task Orchestrator — в изпълнение

- Всяка инструментална задача получава owner-scoped durable run във Firestore.
- Run-ът има статус, план, checkpoint-и и ограничени действия `pause`, `resume`
  и `cancel`.
- Чатът връща `taskRunId`, а изпълнението записва `planning`, `running`,
  `waiting_confirmation`, `partial`, `completed` или `failed`.
- Следва: възстановяване на незавършен run при ново съобщение и видим списък с
  активните run-ове в сайта.

## 3. AI Council — първа реализация приета

- Бутонът „Три AI“ или изрична заявка пита OpenAI, Gemini и Grok независимо.
- Отговорите се показват поотделно; OpenAI прави отделен структуриран арбитраж
  с препоръка, обосновка, рискове и следващи стъпки.
- Council режимът не изпълнява външни действия. Изпълнение започва само след
  избор и точно потвърждение.

## 4. Избор → разрешение → изпълнение

- Избраната препоръка се превръща в Task Orchestrator план.
- Capability Engine проверява ролята, интеграцията, разрешението и риска.
- Разрушителни, външно изпращащи и GitHub write действия спират преди действие
  и искат еднократно потвърждение.
- Всеки резултат и отказ се записва в audit журнала.

## 5. Постоянен интерфейс в сайта

- Панелът показва съвета на трите двигателя, избраната препоръка, активния run,
  последния checkpoint и причината за пауза.
- „Продължи“ използва същия `taskRunId`, не създава скрита нова задача.
- Профилите остават изолирани; тестовият профил не получава owner-only writes.

## 6. Приемане и deployment

1. Пълният unit/integration набор е зелен.
2. Owner browser smoke проверява Council → препоръка → потвърден инструмент.
3. Production smoke проверява exact SHA, readiness, Firestore и auth.
4. Cloud Build GitHub trigger се настройва и се доказва с малък безопасен PR.
5. След exact-SHA deploy се прави визуална проверка на cloudaicore.com.

Текущата честна граница: production deploy-ите са проверени ръчно, но GitHub →
Cloud Build trigger още не е доказано свързан.
